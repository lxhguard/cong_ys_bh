番茄小说 · 技术专项

PIA 秒开方案在书圈与机器人详情页的落地

React · Worker · NSR · Snapshot · Slardar

背景

书圈指标持续负向，定位后确认根因是首屏 4s——这是首屏体验生死线。但书圈交互太复杂，迁不动 Lynx；纯 H5 又压不住渲染成本。我主动立项，在「继续优化 H5 / 迁 Lynx / 上 PIA」三条路线里做技术选型，最终选 PIA 路线并负责从方案设计到上线全链路。

核心动作

  • 方案拍板：分组实测——线上对照 3014ms / Worker 只 prefetch 不渲染反而 3411ms（worker 启动本身有成本）/ Worker 全量 step1-4 压到 2294ms，用数据证明「prefetch 必须配 Snapshot 渲染」才最高效。
  • 架构设计：设计双入口——pia-prefetch.ts Worker 并行承接 step1-4 请求，globalProps 注入消掉 step3 等待；主线程不等数据，直接拿 Snapshot 直出。
  • 快照策略：按 forum_id + tab 做 Snapshot 缓存，maxAge 600s（线上数据：1h 复访率 22%、10min 内 18%）
  • 风险兜底：5s 超时回退 webview 三级降级链路，防止 PIA 本身出问题把页面搞挂；全量 Slardar 监控埋点，上线后可观测。
  • 团队沉淀：把书圈 + 机器人详情页的落地经验沉淀成「番茄 PIA 接入规范」，后续业务方按规范接入，NSR 生效效率 83%。

结果

  • 4s → 2.1sPIA 书圈 FCP（−47%）
  • 600ms / 107msNSR 机器人详情页，安卓 / iOS 75 分位 FCP
  • 83%NSR 生效效率，输出团队 PIA 规范

        PIA（Progressive Instant Web Application）是字节内部的高性能 H5 研发方案，由 PIA Kit（前端研发框架）和 PIA SDK（客户端 Webview 能力）两部分组成。

        它解决的核心问题是首屏速度：把「发请求 → 等数据 → 渲染」的串行链路，改造成「Webview 启动时并行拉起 Worker 预请求 → 业务代码执行时直接消费数据」的并行链路；再叠加 NSR 直出和 Snapshot 复用。

        PIA = Progressive Instant Web Application
        专注 Mobile Web 的高性能 H5 整体方案 · PIA Kit（前端研发框架）+ PIA SDK（客户端 Webview 能力）
        ① 整体架构（5 层）
        业务页面层 React / Preact / SSR · 目录约定 src/pages/<page>/{index.tsx, prefetch.ts}
        ▼ 构建产物（JS + 注入 pia-manifest）
        PIA Kit（研发框架） CLI dev/build/deploy · Builder 构建器 · 插件体系 · 收集 Prefetch 函数 → 构建成 Worker 产物
        ▼ 注入 Runtime
        PIA Runtime Worker 生命周期调度 · 端内/端外模式 · 数据连接与消费 · API：prefetch() / usePrefetch / tracker
        ▼ 通信
        PIA Worker VMSDK（底层 QuickJS，语法兼容 ES2020）· 运行 prefetch.js / nsr.js · 支持 Fetch、Timer、URL、URLSearchParams 等 Web API 子集 · GlobalProps（设备/宽高/应用ID）
        ▼ 端能力
        PIA SDK（客户端） 域名 Settings 白名单 / URL 参数 pia=1 · 解析 pia-manifest · 拦截 HTML 缓存 → Snapshot / NSR 直出
        ② 性能优化三件套
        Prefetch · 预请求（核心能力）
        Webview 启动时并行拉起 Worker 提前发 API 请求，业务代码执行时直接消费数据 → 降低首屏「请求」耗时
        NSR · 前置渲染
        前置页面提前执行 NSR JS Bundle 生成 HTML 存内存，打开即「直出」；整体收益低、排查难，官方建议改用 resources-warmup
        Snapshot · 快照
        二次打开与首次内容差异极小 → 直接复用首次渲染结果
        ③ 两种端模式
        端内模式
        运行于支持 PIA 客户端环境，Prefetch 在独立 Worker 线程发起，时间更早，更快
        端外模式
        普通 Webview：解析到 <head> 即开始预请求，仍快于 componentDidMount 型 React 应用
        ④ Prefetch 为什么快：串行 vs 并行
        传统 CSR（串行）

        Lynx 是字节自研的「用 Web 技术栈快速构建 Native 视图」的高性能跨端框架。

        诞生原因是嵌入式视图场景（卡片嵌在 Native 里）对渲染性能要求极高，而 RN / 小程序（JS 驱动视图更新，首屏依赖 JS 初始化速度）和 SSR（服务端压力大）都容易白屏 / 闪烁。

        Lynx 的核心破局点是首屏直出：DOM 构建全部放在 Native 层主线程，前端产物编译成 Lepus 字节码预编译下发，JS 线程只跑业务逻辑不阻塞 UI。技术栈上自研了

        技术栈上自研了 Lepus 虚拟机（→LepusNG）、Starlight 排版引擎（替代 Yoga）、自渲染引擎（Skia）三件套。

        生态上分两条 DSL：ReactLynx（类 React，整页）和 TTML（类小程序，卡片），各自都经历了三代演进。

        官方当前技术选型口径：整页用 ReactLynx 3.0、重交互的页卡用 TTML nodiff、无交互的页卡用 TTML Air。

        PIA 书圈 · PIA 预请求首屏优化
        FCP 4s → 2.1s
        背景

        书圈是番茄端内 H5 主阵地，但相关实验业务指标持续负向，无法排除是否受首屏加载拖累；多份评测报告也显示端内 H5 首屏加载速度劣于竞品。社区 H5 交互 / 逻辑复杂，直接迁 Lynx 会遇到组件过重、滚动性能差、开发效率低的问题——需要在 Lynx 之外，找一条兼顾性能与迭代效率的跨端路线。

        排查分析

        第一步：拆解首屏链路，定位串行瓶颈完整首屏数据获取需经过四步串行依赖：

        节点 step1 step2 step3 step4
        内容 进入即请求 对预加载数据依赖 对圈子完整数据依赖，结束后渲染骨架屏 骨架屏后异步更新，首屏完成

        每步都要等上一步返回才能继续——这是天然可并行化的对象。原实现 index.tsx 只跑 step1–3，step4 的 get_mixed（tab 数据）留在 App.tsx 里串行等待。

        第二步：关键决策——Worker 边界划在哪？做双分支实测PIA 的核心是把首屏请求挪进 Worker 并行执行，但「挪多少进 Worker」不能拍脑袋。用斩神书圈做三组对照，7 次取均值：

        方案 首屏均值 结论
        线上 webview 对照 3014ms baseline
        Worker 只跑 step1–3，get_mixed 留 webview 3411ms 反而更慢——get_mixed 仍在 JS 线程排队等执行
        Worker 全量 step1–4（最终方案） 2294ms 首屏请求全量并行进 Worker 才是正解

        第三步：并行化中压缩串行链Worker 内 JSB 数据注入 globalProps：step3 的两个非首屏接口迁走，剩余的 getIsAuthor 可由 globalProps 直接得出、提前到 step2——Worker 里 step3 整个消失。

        第四步：复访场景二次加速书圈 1h 内重复进入率均值 22%、10min 内 18%——复访占比不低，使用 Snapshot 让二次进入直接看上次快照。

        解决方案
        • 双入口改造：pia-prefetch.ts Worker 承接 step1–4 全部首屏请求；App.tsx 兼容 PIA / webview 两套逻辑——有 props 走 props，没有自行请求；非首屏接口后置 componentDidMount。
        • Snapshot 复访加速：replace 模式快照，forum_id + tab 为命中 key、10min 有效期；Worker 成功存完整快照，失败也存不完整快照兜底。
        • 三级兜底：Worker 失败 / 5s 超时 → 回退 webview 自行请求；PIA 能力未开自动降级；线上出问题服务端直接关实验。
        • 工程沉淀：getUrlParams 等通用逻辑抽 SDK 兼容 Worker / webview 双环境；全量 Slardar 监控（SDK 命中率 / Prefetch 生效率 / 降级率 / 快照命中率），Worker 错误 throw 到 webview 侧上报。
        收益

        真实DOM的FCP 4s → 2.1s 由于页面使用了Snapshot，因此页面级FCP是800ms左右。该需求沉淀了一套番茄业务的通用PIA能力，可供其他业务直接使用。

        帖子详情页秒开 · 伪 SSR 首屏直出
        FCP 1.5s → 160ms
        背景

        短故事详情页是故事社区消费路径的核心页面，原 webview 链路 FCP 约 1.5s——webview 打开后要串行经历「建连 → 下载完整 JS bundle → 启动 React 运行时 → 请求详情数据 → React render」，首屏出现前用户长时间白屏。

        排查分析

        第一步：拆解 1.5s 的耗时构成首屏慢不是单点问题，是四段串行叠加：① bundle 体积大、下载耗时；② React 运行时初始化耗时；③ 详情数据要等页面 JS 跑起来才发请求；④ React render 才能出首屏。只要其中某一段还在串行等，优化就到不了极致。

        第二步：关键判断——首屏能不能不依赖完整 bundle 和 React 运行时？真 SSR 服务端改造重、收益不确定；于是走「伪 SSR」路线：把首屏数据和首屏渲染都提前到 React 初始化之前完成，让用户先看到内容，React 在后台接管交互。

        解决方案
        • 数据预注入：客户端在预加载阶段拿到详情数据，经 setAppStorage 注入 window.__globalProps；页面 JS 一执行即可同步读取，省掉「页面跑起来再发请求」的一整段串行。
        • 独立入口 + chunk 前置：新增 before-init.ts 独立入口文件，webpack 拆分出 pageinit chunk 前置加载——在 React 运行时启动前先读 globalProps 直出首屏内容，绕开 React render。
        • 图片秒开兜底：客户端 feed 流图片提前转 base64 + 双队列 LRU 缓存池，经 getOfflineImages / getOfflineEmoji 注入 globalProps，首屏 Avatar / FullImage 零请求无缝展示。

        排查分析

        第一步：先问「为什么安卓没事」同一个 bundle、同一份代码，安卓正常、iOS 闪白——差异一定在两个平台的渲染引擎上，而不是业务逻辑。把排查方向从「代码 bug」收窄到「WebView 内核行为差异」。

        第二步：定位到脚本加载时机对照安卓 Chrome 内核与 iOS WebKit 的脚本加载行为，锁定差异：项目用 <script defer> 让 JS 异步加载、不阻塞 HTML 解析——但 iOS WebKit 下 defer 行为不生效，脚本变成了同步阻塞：HTML 要等脚本下载完才继续解析渲染，白屏期间没有首屏内容输出，就表现为闪白。

        当时的排查过程其实很费劲，搜索“iOS webView白屏”得到的都是无效方案，我当时灵机一动，想着是不是内核问题，所以我决定查找词条“script添加defer在safari不生效”，被我找到了一篇文章脚本下载会阻塞 Mobile Safari 首屏渲染

        第三步：确认这是内核级差异，不是配置问题不是脚本路径错、不是缓存问题，而是 WebKit 对 defer 的实现与 Chromium 不一致——靠改业务代码绕不过去，必须改造脚本注入方式本身。

        解决方案

        问题根因是：HTML 里所有 JS 都用 <script defer> 引入，WebKit 下 defer 失效变成同步下载——几个大 JS 没下完之前，HTML 一行都不渲染，连 body:black 的 CSS 都来不及生效。解法不是再调 WebKit，而是换一种脚本加载方式（开发一个叫 DynamicScriptTagPlugin 的webpack插件，这个插件是基于 HtmlWebpackPlugin 扩展）：

        1. 把 JS 按「首屏需不需要」切成两堆

        • 第一堆（首屏必需，就一个小文件 before-init.js，几 KB）：从 defer 名单里摘出来，不带 defer、直接静态写在 HTML 里。它小，同步下载 + 执行也就瞬间的事——执行完第一件事就是读 globalProps 直出黑色骨架，body:black 立刻生效，白屏从源头消失。
        • 第二堆（非首屏，React 主 bundle 等大文件）：不再写死在 HTML 的 <script> 标签里（只要写在 HTML 里，WebKit 就会把它当阻塞资源等它下完）。改成首屏出来后，由 JS 运行时 createElement('script') 动态插到页面上——它慢慢下载、下完 React 才启动接管，这时候用户早就看到黑底内容了。

        2. 用 webpack 插件自动化这套拆分手写 HTML 容易出错，于是写了 DynamicScriptTagPlugin 挂在 HtmlWebpackPlugin 上：构建时自动找到 before-init.js 这个切点——切点之前的脚本保留静态标签（并剥掉 defer），切点之后的脚本从 HTML 里删掉、改由一段内联的「动态加载器」在运行时插进去。每页约定俗成：有 before-init.ts 源码就自动走这套流程，业务侧零配置。

        3. iOS 专项兜底UA 判断是 iOS 且页面不在 prerender 态时，动态加载大 bundle 前多等 20ms，确保首帧已经画完、绝不和它抢渲染。

        收益

        iOS 闪白问题清零，伪 SSR 方案双端对齐上线；夜间模式历史遗留闪白同步根治；插件沉淀为工程级基建，后续所有 H5 页面按同一规则产出脚本注入。

        1.1 私人空间的现状

        私人空间是员工日常接收、草拟、上传、保存、沉淀资料的高频入口，承接了 JoySpace 文档、慧记会议纪要、别人发送的资料、鲸盘文件、课程、外部链接、本地电脑文件等多类内容。但在真实工作中，个人知识资产长期处于 「不断产生、分散存放、难以复用」 的状态——每天产生大量材料，最后既找不到、也复用不了，更难沉淀成可持续使用的经验。

        1.2 四个核心痛点

        问题 具体表现
        内容分散，线上线下难统一管理 工作文档、会议纪要、本地文件、鲸盘资料、课程、外部链接散落在不同入口，线上文档与本地文件分开管理，难以形成统一的个人知识入口
        文档越积越多，查找和复用困难 目录越来越乱，文档越堆越多；记得「写过」却找不到、分不清哪个是最新版本；资料存下来后很难进入问答、总结、方案创作等工作场景
        经验容易流失，个人沉淀难转化为知识 项目结束后，关键决策、踩坑过程、复盘经验没有沉淀；下次遇到类似问题还要重新摸索，个人经验难以被团队复用
        整理成本高，用户不愿持续维护 用户不是不愿整理，而是不知道怎么分类、手动搬移成本高、怕整理后找不到原文件，每次都要重新思考，难以形成习惯

        1.3 解决思路：从「手动整理」到「轻确认整理」

        1. 用 AI 帮个人统一管理、自动整理、持续沉淀知识，让用户从「手动整理文件」变成「轻确认整理结果」；
        2. 将个人经验转化为可复用、可发布、可被组织调用的知识资产，推动个人提效进一步转化为组织提效。

        1.4 竞品视角（我们的差异化在哪）

        主流产品已具备 AI 写作、搜索、总结、问答、标签、分类推荐、文件整理建议等能力。对比后的结论：

        • Notion AI 强在结构化知识库内的智能补全 → 我们强调对非结构化、多来源私人空间文档的整理能力；
        • Google Drive / Gemini 已能「推荐 + 确认后移动 + 撤销」 → 我们进一步突出：不仅移动文件，还沉淀整理规则、支持 Skill 复用、跨来源知识治理和整理历史；
        • 钉钉文档 有 AI 搜索与协同整合 → 我们强调私人空间批量归档、整理前后影响报告、重复/过期风险识别、确认后同步目录；
        • 腾讯文档 偏内容生产与总结问答 → 我们避开单纯内容生成竞争，突出「个人知识治理」和「自动归档闭环」。

        • ② 整理预览：AI 分析完成后给出结果摘要，用户确认方案，包括散落文档数量、涉及目录与主题、本次基于的整理方案。
        • ③ 整理执行日志：展示执行过程（文档移动、验证根目录无散落文档等）；支持动态节点轮播展示进度，可展开查看历史执行流。

        2.1.5 异常处理与历史备份

        异常处理规则：

        • 大模型无法判断归属的文档 → 保留在原位置，不做强制移动；

        历史备份机制：

        • 每次整理生成一个以整理时间命名的子文件夹，并展示快照数量；
        • 历史备份属于系统保障目录，不计入用户目录骨架变更，独立展示在目标目录树底部。

        • 更安心：历史备份机制 + 异常文档保留原位置，整理过程可回溯、可恢复。

        3.2 业务/平台收益

        • 效率提升：AI 打标 + 自动分类，整体文档管理效率提升。

        3.3 一句话总结

        用 AI 把私人空间从「文件堆放处」变成「个人知识管理入口」，让知识存得清楚、找得到、能复用，同时把整理的选择权和安全感留给用户。

        一、为什么要做这件事（Why）

        1.1 背景：两个首页，两种心智

        JoySpace 现有两个首页入口，各自解决不同问题：

        • 文档首页：解决「我现在要处理什么」，是工作流入口；
        • 个人空间首页：解决「我的知识资产是什么状态」，是知识资产管理入口。
        维度文档首页个人空间首页
        核心目标工作流入口知识资产管理
        用户心智「今天要做什么」「我积累了什么」
        时间维度短周期（今天/本周）长周期（月/年）
        内容组织按任务、动态、协作按知识、主题、关系
        信息密度低、但需要精准高、可探索
        典型动作打开/编辑/跟进沉淀/归档/关联

        1.2 痛点：待处理事项和待归档文档，都在「打游击」

        问题具体表现
        待处理事项入口分散评论、@、文档内待办、GTD、提醒阅读、日程材料未读、权限申请等，散落在消息、通知、文档等多个入口，用户需要「到处找活干」
        今天要做什么，说不清缺少一个统一收敛「我欠别人的事」的工作台，容易漏掉临近 deadline 的事项
        收到的文档堆积不整理近两周收到的会议材料、项目文档、周报日报、汇报材料散落在「我收到的」列表里，看完就沉底，很难沉淀进知识体系
        整理成本高、不愿动手用户需要自己判断「这个文档该放哪」，手动建快捷方式、找目录，成本高且难坚持

        1.3 解决思路

        在文档首页新增「工作总结」Tab，作为用户的文档相关工作台，与「我收到的」等 Tab 并列，一个页面内承载两件事：

        1. 待处理：把 7 类待处理事项统一收敛成卡片，支持一键跳转处置；
        2. 待整理：把近两周收到的文档自动分类，并推荐归档目录，支持一键归档。

        让用户从「到处找活」变成「打开一个页面，事情就在那里」。

        逾期处理：逾期待办（如 GTD 超出有效期、待办超时）放置在列表最前方，并在卡片上展示「已逾期」；无时间节点的事项（申请、评论）随新待办展示而受影响排序。

        状态流转

        • 用户点击「已解决 / 完成解决」后，事项进入「已解决」菜单；

        • 已处理卡片上仅保留事项名称 + 文档链接，且不支持把已解决状态改回待处理；
        • 用户通过其他渠道打开文档/回复评论时，当前页面待处理不变，刷新页面后自动拉取最新状态并变更为已完成。

        卡片形态

        • 最简形式：卡片标题（事项摘要，最多 1 行，超出显示 …）、来自（文档标题）、行为（待处理/待回复等）；
        • hover 后展示按钮，支持快速处置；
        • 点击卡片展开完整信息：标题、来自、补充信息、行为、临近时间节点的提醒；
        • 卡片失焦后回到最简形式；
        • 已处理卡片：标题、来自、处理时间；展开后可点击「查看详情」进入对应文档。

        云文档小组件 SDK 技术方案
        @jd/joyspace-jskit-sdk · Host/Client 隔离 · 插件化

        仿照飞书「云文档小组件」客户端 API 形态，基于现有 jskit-sdk 沉淀底座包 @jd/joyspace-jskit-sdk，形成 JoySpace 最佳融合方案。

        背景与目标

        完成 Host/Client 基础通信能力（API 注册注销、中间件链、基础限流、iframe/微前端双通信模式），同时对齐三件事：

        1. 插件化：各能力域 API 以插件方式挂载/注销到 SDK；
        2. 安全隔离：Host 代码不暴露给业务，防止被 Hook 篡改；
        3. 治理能力：API 权限控制 + 三级限流。
        方案选型
        方案 优点 缺点 适用
        npm 包 类型安全、Tree Shaking、构建时集成 需发版、宿主需重构建 底座核心、稳定能力
        微前端运行时 动态加载、热更新、独立部署 运行时开销、版本协调复杂 业务插件、频繁变更

        最终采用 npm 底座 + 宿主内置插件 的 Host/Client 完全隔离架构。

        三层架构
        • Host Runtime（底座 Host，完全封装不对外导出）：消息处理、路由、插件管理、中间件管道；宿主应用加载时自动初始化，业务方拿不到 Host 代码，只能通过 MessageChannel 通信；
        • Client SDK（底座 Client，对外导出）：统一调用代理，API 调用序列化为消息、Transport 收发、事件 on/off/emit、超时控制，完整 TS 类型定义；
        • Capability Plugins（业务能力 Handler）：在宿主应用内实现（document / selection / block 等），通过 __registerPlugin__ 协议挂载，支持 __unregisterPlugin__ 卸载。

        通信通道：iframe 场景走 postMessage，同域微前端走 BroadcastChannel，统一收敛到同一条 Host pipeline。

        核心链路

        请求从 Client 发出 → MessageChannel → Host 侧 MessageHandler → MiddlewarePipeline（Validation → AuthZ → RateLimit）→ ApiRouter 路由到具体插件 Handler → 响应原路返回。

        权限控制（AuthZ）
        • 调用域（Scope）：GLOBAL / SPACE / FOLDER / DOCUMENT 四类，相互独立；每个 API 声明可在哪些域被调用；
        • 权限（Permission）：PAGE_READ / PAGE_EDIT 等；
        • 校验顺序：先判断调用域是否匹配（不匹配直接 SCOPE_MISMATCH，短路），再判断调用方权限是否满足（不满足 FORBIDDEN）。
        三级限流

        从粗粒度到细粒度依次拦截，尽早拒绝超限请求：

        • Host 级 1000/s（保护整体不被打爆）；
        • 应用级 100/s（单应用不影响他人）；
        • API 级 10/s（写操作额外收紧到 5/s，支持单 API 自定义覆盖）。

        算法选型：滑动窗口计数 而非固定窗口——固定窗口在边界会出现 2 倍突发（0.9s 打满 10 个 + 1.1s 又打满 10 个，200ms 内过 20 个请求），滑动窗口任意 1s 窗口内严格受限。

        插件卸载安全底线

        API 从 Router 移除 → schema/权限/限流配置清理 → 事件订阅/定时器/缓存释放 → microfrontend 场景同步移除 window 挂载，避免内存泄漏与野调用。

        错误码体系

        INVALID_PARAMS / SCOPE_MISMATCH / FORBIDDEN / RATE_LIMITED / API_NOT_FOUND / HOST_UNAVAILABLE / CHANNEL_ERROR / TIMEOUT。

        技术分享：前端跨端技术演进、选型，以及 Lynx 原理
        跨端流派 · Lynx 架构 · 业务接入
        为什么要跨端

        一个产品要覆盖 iOS / Android / Web / 小程序 / 桌面 / 鸿蒙，每端各建团队会带来：研发成本高（多套代码重复劳动）、协作效率低（需求同步、联调、发版难统一）、体验不一致。跨端的本质就是 write once, run anywhere——只要业务有降本增效诉求，跨端就会被持续关注。

        在2025年，AI已经基本磨平了各端的开发成本，每个开发者都可以在AI的辅助下成为初级全栈工程师。

        三大流派（2025 年万物归宗）
        流派 判断标准 代表 优势 劣势
        Web 流派 是否由标准 HTML 元素渲染 H5（React/Vue）、Cordova、PWA、PIA 动态化强、成本低、兼容好 性能有天花板、受 WebView 限制
        Native UI 流派 是否由原生组件渲染 RN、Weex、Lynx、Hippy、Kraken、小程序 动态化强、FEer 上手快、体验接近原生 JSB 通信开销、受 iOS 动态化政策限制、强依赖客户端
        Self-rendering Engine 是否自带渲染引擎 Flutter 渲染链路短、60fps、各端一致 动态化弱、包体积大、学习成本高
        小程序：Native UI 流派里的「奇葩」

        微信小程序是混合渲染：用 WebView 承载视图，但 WebView 里渲染的不是标准 HTML，而是客户端 SDK 提供的原生组件——既占了原生组件，又占了 WebView 容器。双线程模型（视图层 / 逻辑层分离）的核心设计考量是安全：JS 能直接操作 DOM，所以把 JS 线程剥离出去沙箱化。Lynx 早期直接参考了这套双线程设计。

        字节 Lynx 是怎么来的
        • 背景：2020 年底内部完成，2021 年高层要求各业务线必须接入；业务方苦 Lynx 久矣（开发效率低、双端 bug 多、oncall 慢）；
        • 演进：2022 年 RL2（Class）+ TTML radondiff；2023.12 试点 RL3（Hook，双端 bug 基本抹平）+ TTML Air / Nodiff，2024 年业务陆续接入；
        • 诞生动因：RN/H5/小程序首屏都依赖 JS 初始化速度，SSR 又有服务端成本；嵌入式卡片/弹窗场景白屏闪烁，需要更好的动态下发和原生体验。
        Lynx 核心架构
        • Lepus 虚拟机：基于寄存器的 JS 子集解释执行器，编译期把 lepus.js → 字节码 → template.js，运行时解释执行生成 VDOM；
        • VDOM → C++ diff → Native UI：RN 是 JS 做 DomDiff 再通过 JSB 同步到原生，瓶颈在 JS 线程；Lynx 把 VDomDiff 下沉到 C++ 层，JS 只 setData，渲染不阻塞 JS；
        • 首屏直出：把 DOM 创建放在 Native 侧，lepus.js 作为 native 可消费的 snapshot 直接首屏秒开；再执行 app-service.js 建立 Native UI 与前端数据的关联；
        • 数据回设：2.x 时代概念（JS 侧向 native 发了无效通知），RL3 已抹平，开发者无感。
        开源版（RL3）现状
        • 基本对标 React Hooks，常规场景无双端 bug；内部各业务从 RL2 迁 RL3 后 actualFMP 提升 3%~11%（抖音商城顶 tab 即 RL3 页面）；
        • 首屏够快、离线化可秒开、开发体验对齐 H5；
        • 仓库：github.com/lynx-family。
        业务接入调研框架

        评估是否引入时要覆盖：

        • 可行性：平台支持（开源版暂不支持鸿蒙）、UI 库是否开源、Node 版本基建、JSB 基建、oncall 入口；
        • 成本：SDK 接入周期与包体积、长期维护（框架升级 + 人才培养）、存量迁移策略；
        • 风险：框架成熟度与断更风险、双版本兼容（有无 SDK 的页面隔断）、试点性能是否达预期、与原生发版流程如何协同；
        • 节奏：试点 → 小范围推广 → 全面落地（增量先行、存量渐进）。
        Chrome Web MCP 调研
        Web Model Context Protocol · 2026.2
        本文摘要
        1. 推出时间：2026.2.10，谷歌推出 Web Model Context Protocol（网页模型上下文协议），目前已通过正式草案，预计 2026 年中后期推广。
        2. 是什么：JSON-RPC 网站——网站 JS API 的标准化，让网站在浏览器里暴露「工具」给 Agent。
        3. 解决什么问题：AI 识别网页从视觉（截图 + DOM 抓取）转为结构化（网页开发者提供 API），解决 AI 理解网页不精准、MCP 服务端压力大等痛点。
        4. 怎么用：网页开发者通过 registerTool 注册工具，AI 通过 executeTool 调用。截至 2026.2.27，官方仅提供浏览器插件「Model Context Tool Inspector」，笔者通过官方编译产物找到 navigator.modelContextTesting.executeTool 在 Canary 可用。
        5. 环境兼容性：仅 >146 版本的 Canary 浏览器支持。
        6. 用途：大厂定制浏览器（如 ima 等）可直接内置 Web MCP 能力，司内业务闭环消费，形成统一标准。
        7. API 分类：
          • 声明式 API：<form> 能力（toolname / tooldescription / toolautosubmit / agentInvoked）；事件监听（toolactivated / toolcancel）；CSS 能力（:tool-form-active / :tool-submit-active）。
          • 命令式 API：网页开发者消费 navigator.modelContext（registerTool / unregisterTool / provideContext / clearContext）；AI 调用者消费 navigator.modelContextTesting（executeTool / listTools / registerToolsChangedCallback / getCrossDocumentScriptToolResult）。
        背景

        业界目前用 AI 理解网页的经典方案是 Browser Use：利用外部 Python 进程 + LLM，像用户一样操作浏览器（点击、输入、滚动）。原理是发送「网页截图 + DOM Tree」给大模型，由模型理解交互元素后模拟用户行为；AI 浏览器插件类似，但会精简抽离 DOM 减少 token，再通过 serverId 消费。

        痛点：

        • 可靠性差：依赖 DOM/布局/截图，页面改版就失效；
        • 性能差：多步「模拟用户操作」延迟和开销大；
        • Token 消耗大；
        • 网页反爬机制；
        • 大部分 MCP 是 server-to-server，涉及前端操作时还要搭后端代理处理跨域。

        Web MCP 思路：把网页进行 SDK 标准化，统一对外暴露自定义 API，AI 通过调 API 操作网页。本质是把 MCP 生态从服务端集成转向 AI 基建——AI 不去理解网页视觉形态，而是把网页当 SDK 调用。网站开发者用 navigator.modelContext 向浏览器注册「工具」。

        官方定义：

        • WebMCP 官方：developer.chrome.com/blog/webmcp-epp
        • W3C 草案：webmachinelearning.github.io/webmcp/
        API

        声明性 API：通过标注 HTML 表单元素让 Agent 理解页面交互能力，适合简单场景（类似语义化 HTML，对机器可读友好）。

        <form
  toolname="jooyspace_web_link"
  tooldescription="云文档网络连接"
  toolautosubmit
>
  <input name="title" type="text" placeholder="填写标题" />
  <input name="link" type="text" placeholder="填写链接" />
  <button type="submit">提交</button>
</form>
        • submit 事件新增 agentInvoked 布尔属性（Agent 触发时为 true），可 respondWith(Promise) 返回工具结果；
        • toolactivated：Agent 调用工具且表单字段预填后触发；toolcancel：用户取消或表单 reset 时触发；
        • CSS 伪类：:tool-form-active（作用于 form）、:tool-submit-active（作用于提交按钮）。

        命令式 API：开发者注册/注销工具，Agent 灵活调用，适合复杂交互。

        navigator.modelContext.registerTool({
  name: 'getDoc',
  description: '获取文档信息',
  inputSchema: { pageId: 'xxxx' },
  execute: async (args) => { /* 业务逻辑 */ }
});
navigator.modelContext.unregisterTool(toolName);   // 移除单个
navigator.modelContext.provideContext({ tools: [...] }); // 批量注册
navigator.modelContext.clearContext();              // 清空全部
        调用方式

        截至 2026.2.27，Canary 147.0.7707.0 官方未推出消费端代码。

        官方调试：装浏览器插件「Model Context Tool Inspector」（Chrome Web Store），相当于 Agent，可查看/调用页面注册的工具做开发调试。需用 npx serve 起 HTTP 服务（插件读不了 file://）。

        读源码找到的测试 API：打开 Canary 的 Extensions 目录，查插件 id 对应文件夹的 content.js，发现 Canary 实际消费的是 navigator.modelContextTesting（官方未公开，仅建议玩具尝鲜）：

        • executeTool(name, inputArgsString)：入参传 JSON 字符串，不要传对象；
        • listTools()：列出所有注册工具；
        • registerToolsChangedCallback(fn)：工具增删时触发回调；
        • getCrossDocumentScriptToolResult：跨文档（新页面/iframe）场景拿工具执行结果。

        环境开关：chrome://flags 搜索 WebMCP，开启 #enable-webmcp-testing。

        开发 Demo

        实现一个列表「增删改查」页面，注册 4 个工具：listAdd / listDelete / listUpdate / listQuery，在 Inspector 插件里手动传参调用，工具执行后页面列表实时增删改查，返回结构化文本结果。

        价值
        • Web MCP 可能成为类似 fetch 的浏览器基建能力，接入 Web MCP 等于拿到 Agentic Web 入场券；
        • 业务价值贴近 RSS，是 RSS 踩中 AI 风口的变体；若成基建，广告植入方式也会进化；
        • 技术价值类似 NSR：压力从服务端迁到客户端，本地运行隐私安全有保障、敏感数据不上云；
        • 一旦成基建，SEO 会更轻松，网站变成真正的 SDK 资源节点；网页能力标准化后，开发者只需写一套 registerTool，各种截图识别型 AI 工具都能统一调用。
